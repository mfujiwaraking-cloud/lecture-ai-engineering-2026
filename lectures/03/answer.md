- 気づき・疑問：
  - docstring の一言で、ツールの呼び方（回数と引数）が3回とも変わった。今回の範囲では、INSTRUCTIONS よりも docstring のほうが「ツールをどう呼ぶか」を直接左右していた
  - 「まとめて」にして1回の検索でも正しく答えられたのは、`_normalize` が空白を消し、「用語名が検索語に含まれるか」の部分一致でも探す実装だったから。`loraqlora` に `lora` と `qlora` が両方含まれるので、たまたまうまくいった。完全一致だけで探す実装なら何も見つからなかったはずで、docstring はツールの実装に合わせて書く必要がある（元の「1つだけ」は実装に合った書き方）
  - 元のままだと、LoRA と QLoRA の定義が2回の検索結果の両方に入る（重複する）ので、入力トークンが多かった（1196 → 885、約26%減）。呼ぶ回数だけでなく、返す内容の重なりもコストに効く
  - 「必ず search_glossary で確認する」を消しても、検索は止まらなかった。さらに docstring の「答える前に使うこと」まで消しても止まらなかった。ツール名や「講座の用語集から用語を検索し」という説明、「用語集に見つからないことは…」の行、質問の中の「AIE2026」など、残った手がかりだけでもモデルは検索を選ぶようだ。スライドの例のように「検索せずに答える」ようにはならなかった
  - 行を消すたびに、入力トークンが Q1 と Q2 で同じだけ減った（Bで −48、Cで −60）。1回の質問で LLM を2回呼んでいる（requests=2）ので、指示やツールの説明は毎回のリクエストに入っていると考えられる。指示を長くすると、リクエストの回数に比例してコストが増える
  - 疑問：講座と関係ない一般的な質問（例：「Pythonとは？」）なら、Bの状態で検索をやめるのか。モデルを `gemini-3.5-flash` に変えると結果は変わるのか。各3回しか試していないので、Bで「LoRA だけ検索」になったような揺れがどのくらいの割合で起きるかは、回数を増やさないと分からない
